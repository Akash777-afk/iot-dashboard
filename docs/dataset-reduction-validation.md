## Schema (all 22 original columns preserved)

`meter, deviceId, customer, locality, city, firmware, applet, status, security, issueCategory, bts, problem, severity, affectedMeters, sinr, rsrp, rssi, rsrq, transport, appletUpdateStatus, appletAction, lastReported`

No columns were dropped or renamed in the CSV itself. There are two distinctly-named status-like
columns that are easy to conflate — neither was merged with the other:

- **`status`** — the device's live operational/connectivity state: `Active`, `Degraded`,
  `Out of Reach`, `Update Available`, or `Blacklisted`. This is what the app calls "Device
  Status" (Devices table's Status column, the Dashboard status breakdown).
- **`appletUpdateStatus`** — whether that specific device's SIM Applet is `Updated` or has an
  `Update Available`. This backs the SIM Applet page's Compatibility/Action columns
  (`appletAction`: `Update` vs `Check`) and is independent of the device's operational status
  above (an `Active` device can still need an applet update).

`src/data/devices.ts`'s in-memory `MasterRecord` type keeps these separate as `status:
DeviceStatus` and `appletAction: AppletAction`/`ticketStatus` — it does not introduce a naming
collision, so no renaming was needed to avoid breaking the application.
